# Sparse AI distraction-blocker projects: brom.ai, AWF, LockIn MCP, and Distraction Killer AI

Research checked through **2026-11-08**. All web pages and repository snapshots below were accessed on that date unless another access date is stated. Historical posts are used only for historical claims, not as evidence that a prototype still works today. “Static-code finding” means the source was read, not that the extension was executed or that a failure occurs at a measured rate. Searches covered exact names, domains and repositories, LessWrong comments, Hacker News, GitHub metadata/releases/issues, npm, the Chrome Web Store, and vendor documentation/legal pages. Devpost and Product Hunt blocked full retrieval; therefore no claim is made about feedback or details that could not be read there.

## Which exact artifacts are in scope, and what is their current status?

### Takeaway

These are four distinct artifacts, not interchangeable “AI blockers.” Only **LockIn MCP** has directly verifiable current package and store releases in 2026; brom.ai’s experiment was explicitly discontinued, AWF remains a 2023 prototype in its public history, and Distraction Killer AI is a very small 2025 extension repository rather than an evidenced commercial user base. — [brom.ai, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/); [AWF 0.1 release, 2023-09-24](https://github.com/coolvision/awf/releases/tag/0.1); [npm `lockin-mcp` release record](https://registry.npmjs.org/lockin-mcp); [Distraction Killer AI repository](https://github.com/AceAchyut/distraction-killer-ai)

### Cited Findings

#### 1. brom.ai — the discontinued machine-learning Chrome-extension experiment

- The exact artifact is described in brom.ai’s **January 6, 2021** post, “using machine learning to block distractions.” Its author says that during summer 2020 they built a Chrome extension that converted pages and the user’s desired focus topics into topic vectors, then blocked pages too far from those topics. The motivation was contextual access on mixed-use sites: allow computer-science lectures while blocking unrelated entertainment on the same domains. The post explicitly says, **“the project has been discontinued.”** It offers a video demonstration, not a current download or supported service. — [brom.ai project post, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/)
- As checked on **2026-11-08**, the brom.ai homepage contains only minimal site chrome, “brom,” “???,” and a 2021 copyright notice; it does not document a successor or revive the old blocker. The discontinued status is therefore a historical fact from the developer, while the current page supplies no basis to describe brom.ai as an active product. — [brom.ai homepage, accessed 2026-11-08](https://www.brom.ai/)
- The author’s criticism that conventional domain blockers could not distinguish a lecture from entertainment on YouTube is evidence of the **design problem the author wanted to solve**, not a complaint made by a brom user about brom’s performance. — [brom.ai project post, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/)

#### 2. The LessWrong GPT-4 blocker — author’s article and `coolvision/awf` are the concrete artifacts

- The exact LessWrong item is **“GPT-4 for personal productivity: online distraction blocker,”** posted by **Sergii on 2023-09-26 at 17:41:31 UTC**. It is a linkpost to `https://grgv.xyz/blog/awf/`, not itself a separate maintained blocker. The linked implementation is **AWF: AI Web Filter**, in [`coolvision/awf`](https://github.com/coolvision/awf), with downloadable unpacked-extension release **0.1 published 2023-09-24**. — [LessWrong post and dated metadata](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker); [author’s implementation article, updated 2023-09-24](https://grgv.xyz/blog/awf/); [AWF 0.1 release](https://github.com/coolvision/awf/releases/tag/0.1)
- AWF’s own README calls it a **prototype** of an online-distraction extension based on GPT-4. Its manifest is version 0.1, uses Chrome Manifest V3, and injects `content.js` into HTTP and HTTPS pages. The project declares an MIT license. — [AWF README at the sole public commit](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/README.md); [AWF manifest at that commit](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/manifest.json); [repository license](https://github.com/coolvision/awf/blob/master/LICENSE)
- GitHub’s directly retrieved metadata on **2026-11-08** showed one public commit (`init`), one release (0.1, 2023-09-24), no open issues, and `archived: false`. The only public push timestamp was 2023-09-24. This supports saying **no subsequent public code change is visible**, not declaring the repository formally abandoned; `archived: false` and zero issues do not demonstrate active maintenance or correctness. — [AWF repository/API metadata](https://api.github.com/repos/coolvision/awf); [initial commit](https://github.com/coolvision/awf/commit/9b8de42b6031c65f384965aae24b943d66a334ad); [release history](https://github.com/coolvision/awf/releases)
- The implementation sends the page URL plus the first 2,000 characters of visible body text to an OpenAI chat-completion request, with a user-supplied model, prompt, and API key. It caches the decision locally per full URL. This exact data path matters when distinguishing the GPT-4 prototype from generic local blocklist tools. — [AWF `content.js`, pinned 2023 source](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/content.js); [author’s implementation article, 2023-09-24](https://grgv.xyz/blog/awf/)

## What complaints are firsthand reports, and which criticisms are only theoretical?

### Takeaway

The only concrete end-user malfunction found across these artifacts is AWF’s 2023 empty-blacklist bug. AWF also has author-reported cost/latency concerns; LockIn has a real-world architectural security critique and desk-research limitations, while brom and Distraction Killer AI have no located firsthand complaint trail. None of this supports broad statements such as “users hate these tools.” — [AWF blacklist report, 2023-09-27](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker/comment/NiYcrciaFG7hmL7P7); [LockIn HN discussion, 2026-07-04](https://news.ycombinator.com/item?id=48784250)

### Cited Findings

#### brom.ai: no identified user-performance complaint

- The only firsthand problem statement in the project post is the **developer’s experience before building brom**: domain blacklist tools did not meet the need for selective access to educational material on mixed-content sites. The post says a demonstration exists but supplies no user-test findings or accuracy results. It would be misleading to convert this motivation into either praise or complaints from brom users. — [brom.ai, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/)
- The explicit discontinuation is the only located developer outcome/status statement. It is not accompanied by a sourced reason such as classification failures, expense, privacy objections, or lack of adoption; any such explanation would be speculation. — [brom.ai, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/)

#### AWF: one reproducible user bug plus author-run cost/latency evidence

- **Firsthand user defect:** Jay Bailey reported on **2023-09-27 at 00:54:24 UTC** that removing the last blacklist item caused every non-whitelisted page to be treated as blacklisted; adding an item back fixed it, while the rest of the application “looks good.” This is a specific application test, not an abstract prediction. — [Jay Bailey’s LessWrong comment](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker/comment/NiYcrciaFG7hmL7P7)
- The 2023 source corroborates a plausible mechanism for that report: `settings.blacklist.split('\n')` yields an empty string for an empty field, and every URL contains `""`; the loop then calls `blockPage`. This is source-code corroboration, not a newly executed reproduction. — [AWF `content.js`, pinned source](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/content.js)
- **Developer’s own short trial, not independent validation:** Sergii said on **2023-09-24/26** that after a few days the extension made correct decisions “in most cases,” with no denominator or test set. GPT-4 usage reached approximately **$1/day**, which the author extrapolated to roughly **$10–30/month**. These are historical 2023 usage/pricing observations, not current API costs. — [Author’s implementation article](https://grgv.xyz/blog/awf/); [LessWrong post, 2023-09-26](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker)
- The same author reported multi-second OpenAI latency and said waiting could kill research flow/momentum even if it sometimes made browsing more mindful. The fetched article literally renders a malformed upper bound, **“up to 50-10s,”** so the safe finding is “several seconds,” not an invented corrected range such as 5–10 or 50–60 seconds. — [Author’s implementation article, 2023-09-24](https://grgv.xyz/blog/awf/)
- **General self-control critique, not verified AWF use:** Razied wrote on **2024-07-24** that any filter removable through Chrome’s extension menu is “essentially worthless,” citing experience that users eventually “temporarily” disable such tools. The comment does not say Razied tested AWF or provide dates, devices, or an AWF bypass log. Preserve it as a general/design critique about bypass friction, not a second confirmed malfunction. — [Razied’s LessWrong comment](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker/comment/ALgmzmTCXztC2YfKh)
- Other commenters proposed GPT-3.5 for lower cost, putting an explanation before the YES/NO response, and smaller local open-weight models for privacy. These are suggestions/theoretical concerns, not reported benchmark comparisons of AWF variants. — [LessWrong discussion, comments dated 2023-09-26 onward](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker)

#### LockIn MCP: concrete security objection is theoretical; desk reviews are not usage reports

- In the developer’s **2026-07-04** “Show HN,” LockIn’s author called native blocking “unbypassable” and praised timed exceptions. A commenter responded the same day that the Cloudflare relay means a third party sees block/unblock tool calls before they reach the local daemon; they warned that a compromised or misconfigured relay could turn an injected tool call into host redirection and asked for a local transport. This is a specific trust-boundary critique, but **not a reported compromise, arbitrary-redirection incident, or firsthand installation failure**. — [Show HN post, 2026-07-04](https://news.ycombinator.com/item?id=48784250); [comment by opptybiz, 2026-07-04](https://news.ycombinator.com/item?id=48784367)
- Koda Intelligence’s **2026-07-16** review explicitly labels its method **“desk research.”** It lists elevated hosts-file permissions and possible corporate-policy conflict, phones/native apps/DNS-over-HTTPS as potential hosts-based limitations, dependence on supported AI tools, and no permanent free tier. These are reasoned product-fit limitations, not a measurement that each bypass works on every configuration or a customer complaint. — [Koda LockIn profile, tested/filed 2026-07-16](https://www.koda.community/reviews/2026-07-16-lockin-mcp.html)
- Launchtory’s current profile says it is based on public website information and may use AI-assisted analysis. It tells readers to verify integration polish, refunds/cancellations, uninstall/hosts recovery, telemetry/retention, and security-audit posture. These are documentation questions identified by a third party, not demonstrated leftover hosts entries, unauthorized billing, or a breach. — [Launchtory LockIn profile, accessed 2026-11-08](https://launchtory.com/projects/lockinmcp)
- The exact Chrome store entry’s **6 users and one aggregate rating** at access time did not provide a corpus of detailed firsthand reviews from which recurring complaints could be extracted. One rating should not be paraphrased as a typical user experience or a reliable satisfaction estimate. — [LockIn MCP Chrome listing, accessed 2026-11-08](https://chromewebstore.google.com/detail/lockin-%E2%80%93-ai-distraction-b/jbfbolpcbfnljihfapplfnhimokjjkmd)

#### Distraction Killer AI: no located firsthand complaints; do not manufacture them from code

- Direct repository inspection found no user issue reports, release feedback, or README usage results. Its zero public issues cannot fill that silence with either “works perfectly” or “users hate it.” — [Distraction Killer AI issues](https://github.com/AceAchyut/distraction-killer-ai/issues); [repository README at latest commit](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/README.md)

### Inferences

- AWF provides the only useful complaint case study here, and it combines three different evidence classes that should remain separate in synthesis: an end-user reproducing a state-handling bug, the developer’s own cost/latency trial, and commenters’ avoidance/privacy/design opinions. — [AWF LessWrong discussion](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker)
- For self-control products, “can be intentionally disabled” should be labeled an **attacker-is-the-user limitation**, while crashes, overblocking, dashboard failures, and network errors are reliability failures. LockIn deliberately exposes permanent and temporary unblock tools; those options can increase flexibility while weakening commitment, and their existence does not prove an accidental bypass bug. — [LockIn v1.0.20 README/tool table](https://www.npmjs.com/package/lockin-mcp/v/1.0.20?activeTab=readme); [Razied’s general extension critique](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker/comment/ALgmzmTCXztC2YfKh)
- The absence of complaint volume may reflect short lived prototypes, low visibility, or feedback confined to app/Discord/private channels. It cannot establish superior reliability. LockIn’s public store footprint and the two other public repositories demonstrate why the samples are too sparse for prevalence estimates. — [LockIn Chrome listing](https://chromewebstore.google.com/detail/lockin-%E2%80%93-ai-distraction-b/jbfbolpcbfnljihfapplfnhimokjjkmd); [AWF repository](https://github.com/coolvision/awf); [Distraction Killer AI repository](https://github.com/AceAchyut/distraction-killer-ai)

- Product Hunt returned HTTP 403, so LockIn’s listing comments could not be assessed. Devpost returned HTTP 403, so Distraction Killer AI comments and reception could not be assessed. No statement is made that those pages contain either positive or negative feedback.

## What reliability, privacy, security, and project-governance concerns are directly documented?

### Takeaway

The concerns differ materially by implementation. AWF ships page samples to OpenAI and has brittle parsing/state handling; LockIn combines privileged hosts-file control with an optional but real browsing-data/relay trust boundary; Distraction Killer AI’s current code is a static, overly broad rule prototype despite its AI label; brom discloses too little implementation detail for a comparable privacy assessment. — [AWF source](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/content.js); [LockIn privacy policy, July 2026](https://www.lockinmcp.com/privacy); [Distraction Killer AI manifest/source](https://github.com/AceAchyut/distraction-killer-ai/tree/0e4228babfdd068abdb3dea6e1edfe0d980a8974)

### Cited Findings

#### brom.ai: plausible contextual-filtering upside, unmeasured classification/privacy risk

- Brom’s topic-vector approach was aimed at avoiding the all-or-nothing behavior of domain blocklists, which is a documented design goal rather than a measured reduction in false positives. No precision/recall results, example error log, user-set exception workflow, or privacy data-flow documentation accompanies the discontinued-project post. — [brom.ai, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/)
- Because the public post does not say whether page processing was local or remote, it would be unsupported to describe brom either as privacy-preserving local ML or as uploading browsing history. — [brom.ai, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/)

#### AWF: explicit disclosure, narrow sample, and fragile trust boundaries

- **Privacy was explicitly acknowledged by the author:** active AWF sends a sample of every visited page to OpenAI unless a whitelist/blacklist match handles it locally. The author warned that people concerned about sensitive pages or leaking browsing history should avoid the extension. The whitelist therefore has two effects: it permits a page without an LLM decision and prevents that page’s text sample being sent. — [Author’s implementation article, 2023-09-24](https://grgv.xyz/blog/awf/)
- The source shows that the transmitted sample is the **URL plus 2,000 body-text characters**, not necessarily the full page. The narrower claim “full browsing history is uploaded” would be inaccurate; the supported concern is that potentially sensitive URLs and content excerpts are sent page by page for uncached, non-exempt visits. — [AWF `content.js`](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/content.js)
- **Setup/key handling:** the extension runs OpenAI directly in browser content code with `dangerouslyAllowBrowser: true` and stores user settings including the API key with `chrome.storage.local`. This is objective source behavior, not proof that the key was exfiltrated. It does mean AWF’s architecture is not a server-mediated, provider-managed-key design and needs its own sensitive-key threat assessment. — [AWF `content.js` and `main.js`](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/content.js); [settings code](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/main.js)
- **Classification robustness:** only the first 2,000 characters determine an uncached decision, and `a.includes("YES")` treats YES anywhere in the model response as a block. This creates a source-visible risk of wrong decisions from partial context or an explanation containing YES, distinct from the explicitly requested “YES or NO” output contract. No quantitative false-block rate is available. — [AWF `content.js`](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/content.js); [default prompt in author’s article](https://grgv.xyz/blog/awf/)
- **Static security concern, not a reported exploit:** `blockPage` writes `href` and the model-derived `info` into `innerHTML` without escaping, while web-page text can influence the model response. This is a concrete unsafe rendering pattern worth exploit testing, but the research did not establish script execution, assign a CVE, or find an in-the-wild report. — [AWF `blockPage` implementation](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/content.js)
- **Self-control versus enforcement:** AWF is installed as an ordinary browser extension and its local cache/settings can be controlled by the same user. The general concern that an adult can remove such an extension is therefore architecturally understandable, but only Razied’s general critique—not a measured AWF bypass rate—is available. — [AWF manifest](https://github.com/coolvision/awf/blob/9b8de42b6031c65f384965aae24b943d66a334ad/manifest.json); [Razied, 2024-07-24](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker/comment/ALgmzmTCXztC2YfKh)

#### LockIn MCP: privileged local control, remote connectors, scoped browsing collection, and legal-document tension

- **Permissions/system modification are intrinsic:** the package requires administrator privileges to modify `/etc/hosts` and runs a background service for persistence. The vendor terms expressly make users responsible for hosts-file/system-configuration changes and disclaim responsibility for blocking/unblocking damages. This is a documented administrative and recovery burden, not evidence that LockIn actually damaged a machine. — [LockIn v1.0.20 README](https://www.npmjs.com/package/lockin-mcp/v/1.0.20?activeTab=readme); [Terms, June 2026](https://www.lockinmcp.com/terms)
- **“System-level” does not justify “absolutely unbypassable.”** The vendor accurately describes resilience to a new browser profile, private window, another browser, and restart when the hosts entries are honored. Yet the exposed tool table includes both `unblock_domains` and `temporarily_unblock_domains`, and Koda separately notes phones and non-hosts resolution paths as limitations. These are different threat models: convenient bypass within the focus workflow versus deliberately circumventing hostname resolution with another device/network stack. No verified accidental restart/private-window bypass was found. — [LockIn homepage claims](https://www.lockinmcp.com/); [tool table in v1.0.20 README](https://www.npmjs.com/package/lockin-mcp/v/1.0.20?activeTab=readme); [Koda desk-research limitations, 2026-07-16](https://www.koda.community/reviews/2026-07-16-lockin-mcp.html)
- **Relay boundary:** current policy says block lists and MCP configuration stay on the device, while relay traffic is proxied through the vendor’s Cloudflare Worker to connect the AI client to the local MCP server. The HN objection is therefore relevant to trust in remote commands even though no browsing-history upload is implied by hosts blocking alone. The current package documents `--skip-tunnel` for local MCP only, so a relay is not the sole documented connection mode. — [Privacy policy, July 2026](https://www.lockinmcp.com/privacy); [HN relay critique, 2026-07-04](https://news.ycombinator.com/item?id=48784367); [v1.0.20 installer flags](https://www.npmjs.com/package/lockin-mcp/v/1.0.20?activeTab=readme)
- **The optional Chrome extension is not zero-collection.** Current policy says that while connected and focus blocking is active, it may send page URLs for distraction logs and task-aware checks; relevance checks can include page URL, title, and a short page excerpt tied to the LockIn account. It retains active-block-list visits plus short productive dwell on a small set of work sites. The vendor says it does not upload full browsing/search history, sell those data, or pass them to connected third-party AI agents. Both halves—the collection and the limitations—must be reported. — [Privacy policy, July 2026](https://www.lockinmcp.com/privacy)
- Chrome’s current disclosures independently categorize the companion as handling **personally identifiable information, authentication information, web history, user activity, and website content**, alongside developer declarations that data are not sold or used/transferred for unrelated purposes or creditworthiness. This is platform disclosure, not evidence of misuse. — [LockIn Chrome listing privacy section, accessed 2026-11-08](https://chromewebstore.google.com/detail/lockin-%E2%80%93-ai-distraction-b/jbfbolpcbfnljihfapplfnhimokjjkmd)
- The vendor separately collects account email/information, uses secure tokens for licensing/device authorization, uses PostHog/Rybbit/DataFast on marketing pages, sends verification and one abandoned-checkout follow-up email, and sends voluntary bug-report content through Resend. These flows should not be conflated with the local hosts block list or optional extension page excerpts. — [Privacy policy, July 2026](https://www.lockinmcp.com/privacy)
- **License/terms tension:** npm declares the package MIT, while the current website Terms say users may not “reverse engineer” or build a competing product and permit termination for competitive-intelligence misuse. This is an observable documentation tension for someone assessing reuse/company risk, not a legal conclusion about which provision prevails. — [npm package metadata](https://registry.npmjs.org/lockin-mcp/1.0.20); [LockIn Terms, June 2026](https://www.lockinmcp.com/terms)
- Mobile coverage is not included in the desktop blocker claim: the FAQ explicitly suggests pairing with iOS Screen Time for mobile. Thus a household-wide, cross-device control requirement is unmet by LockIn alone; no mobile LockIn outage is being alleged. — [LockIn FAQ, accessed 2026-11-08](https://www.lockinmcp.com/faq)

#### Distraction Killer AI: static implementation contradicts the implied adaptive functionality

- **No visible AI inference in the current source snapshot:** the six implementation/config files contain fixed social-domain and keyword arrays and Chrome extension APIs, with no model/API request or AI dependency. `background.js` blocks six hard-coded social domains; `content_script.js` searches only `reel`, `shorts`, `meme`, `trending`, and `viral`. The README contains only “Real-time AI focus guardian for students.” The supported conclusion is **the repository does not implement the advertised AI behavior in visible code**, not that the Devpost presentation or a private version necessarily has the same limitation. — [Source tree at 2025-12-14 commit](https://github.com/AceAchyut/distraction-killer-ai/tree/0e4228babfdd068abdb3dea6e1edfe0d980a8974); [`background.js`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/background.js); [`content_script.js`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/content_script.js)
- **Focus toggle/state defect visible statically:** `background.js` reads `focusMode` from local storage but never tests its value before closing a matched social tab. `popup.js` merely displays “Focus protection toggled!” and does not update storage, while the popup always displays “Status: Active.” This suggests the visible toggle does not control blocking in the inspected source. It has not been runtime-tested or attributed to user reports. — [`background.js`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/background.js); [`popup.js`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/popup.js); [`popup.html`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/popup.html)
- **False-positive surfaces are source-visible:** social matching uses `tab.url.includes(site)`, which is substring matching on the whole URL rather than hostname equality, and the all-page content script alerts whenever visible body text contains any generic keyword. Consequently URLs that merely contain a social-domain string or educational pages discussing “viral,” “meme,” or “shorts” can match the same rules. These are static inferences about possible matches, not a measured classroom false-positive rate. — [`background.js`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/background.js); [`content_script.js`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/content_script.js)
- **Permission capability versus actual transmission:** `<all_urls>` and the all-URL content script let the extension inspect page body text broadly, but the inspected source only lowercases and scans that text locally; no network-exfiltration call was found in the six files. Therefore a privacy review should flag broad access and absent production documentation, while explicitly **not** alleging that browsing content is sent to an outside server. — [`manifest.json`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/manifest.json); [`content_script.js`](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/content_script.js)
- Public source availability is not the same as permission to reuse: no LICENSE file or declared license appeared in the retrieved tree/metadata. This is a governance/reuse limitation, not a user complaint or accusation of infringement. — [Repository tree/API metadata, accessed 2026-11-08](https://api.github.com/repos/AceAchyut/distraction-killer-ai); [source tree](https://github.com/AceAchyut/distraction-killer-ai/tree/0e4228babfdd068abdb3dea6e1edfe0d980a8974)

### Inferences

- For blockers informed by page content, the central trade-off is richer context versus exposure and classification uncertainty. AWF makes this explicit with OpenAI excerpts and slow/costly remote calls; LockIn narrows what it says is retained but still processes task-relevance excerpts server-side; brom leaves the processing boundary unknown. Neither “AI is inherently private” nor “AI necessarily uploads all history” fits the documented architectures. — [AWF article](https://grgv.xyz/blog/awf/); [LockIn privacy](https://www.lockinmcp.com/privacy); [brom.ai](https://brom.ai/posts/using-machine-learning-to-block-distractions/)
- Hosts-file blocking and extension blocking solve different casual-bypass problems but neither creates a tamper-proof commitment device against a determined device administrator. LockIn’s stronger persistence claims should be retained only with the vendor’s own permanent/temporary override tools and mobile scope in view. — [LockIn homepage](https://www.lockinmcp.com/); [v1.0.20 README](https://www.npmjs.com/package/lockin-mcp/v/1.0.20?activeTab=readme)
- Distraction Killer AI illustrates why a project title should not be used as proof of model behavior. A source-level check found static rules and UI/state defects before any meaningful claim about AI accuracy, bias, educational suitability, or student surveillance could be made. — [Distraction Killer AI source snapshot](https://github.com/AceAchyut/distraction-killer-ai/tree/0e4228babfdd068abdb3dea6e1edfe0d980a8974)

### Gaps

- No independent security audit, reproducible privacy-traffic capture, or measured accuracy/false-positive benchmark was found for any of the four artifacts. Static AWF and Distraction Killer AI observations were not executed; LockIn’s pipeline was not installed, and its server retention duration/audit posture were not established beyond the public policy.
- AWF’s unsanitized `innerHTML` pattern requires controlled exploit validation before calling it a confirmed XSS vulnerability. The HN relay scenario similarly remains theoretical without evidence of a LockIn compromise or injected command.
- Brom’s model/processing details and Distraction Killer AI’s inaccessible Devpost materials leave unresolved whether additional prototypes or documentation implement more than the public sources inspected here.

## What has been officially acknowledged, mitigated, or changed, and what remains unresolved?

### Takeaway

Official disclosures are unusually useful in this sparse set: brom acknowledges discontinuation, AWF’s author acknowledges privacy/cost/latency limitations, and LockIn documents both its privileged architecture and its scoped cloud collection. Only AWF has a visible public user bug report that can be compared with a code history, and no subsequent public fix is visible there; npm release counts alone do not identify LockIn fixes. — [brom.ai](https://brom.ai/posts/using-machine-learning-to-block-distractions/); [AWF article/repository](https://grgv.xyz/blog/awf/); [LockIn privacy](https://www.lockinmcp.com/privacy)

### Cited Findings

#### brom.ai

- **Officially closed historical experiment:** the January 2021 statement that the project was discontinued is clear. The current homepage supplies no documented revival, migration path, release, or support commitment as of 2026-11-08. There is no source-backed basis for saying a bug was later fixed. — [Discontinuation post, 2021-01-06](https://brom.ai/posts/using-machine-learning-to-block-distractions/); [homepage, accessed 2026-11-08](https://www.brom.ai/)

#### AWF / LessWrong blocker

- **Acknowledged privacy risk:** the author explicitly advised people who did not want to risk sensitive-page or browsing-history exposure to avoid the extension and supplied whitelist/blacklist exemptions. Those lists are safeguards against sending matched-page content, not protection against all local-key or rendering concerns. — [Author’s article, 2023-09-24](https://grgv.xyz/blog/awf/)
- **Acknowledged economic and interaction costs:** the author disclosed historical GPT-4 cost, multi-second delays, and the possible loss of research momentum. The suggested mitigation was to test only a few pages per domain rather than every page, but it was presented as an idea needing experimentation, not a completed improvement. — [Author’s article, 2023-09-24](https://grgv.xyz/blog/awf/)
- **Blacklist report response but no visible code fix:** Sergii replied “thanks!” to Jay Bailey’s blacklist report; that is not a written confirmation of a fix. The repository currently exposes just the original 2023 commit and release, so no subsequent public code change can be credited with resolving it. The supported wording is “no public fix is visible,” not “the bug definitely persists in every private build.” — [Bug thread, 2023-09-27](https://www.lesswrong.com/posts/denTWbbYyTfbYLtE5/gpt-4-for-personal-productivity-online-distraction-blocker/comment/NiYcrciaFG7hmL7P7); [AWF commits](https://github.com/coolvision/awf/commits/master/)

#### LockIn MCP

- **Current maintenance is visible:** `lockin-mcp` advanced from 1.0.0 on 2026-06-16 to 1.0.20 on 2026-11-02, and the specific Chrome companion reached 0.3.7 on 2026-08-26. These are release/version facts only; npm’s record does not provide a sourced bug-by-bug changelog, and releases cannot automatically be described as bug fixes. — [npm release history](https://registry.npmjs.org/lockin-mcp); [Chrome listing](https://chromewebstore.google.com/detail/lockin-%E2%80%93-ai-distraction-b/jbfbolpcbfnljihfapplfnhimokjjkmd)
- **Persistence is a stated feature, not an independently verified fix:** current FAQ says blocks persist in the hosts file and a background service maintains MCP/temp-unblock timers across restarts. The current desktop scope distinguishes full macOS support from hosts-based Linux/Windows support. No official release note tying a particular restart bug to a particular fixed version was found. — [LockIn FAQ](https://www.lockinmcp.com/faq)
- **Relay choice is now documented:** the v1.0.20 README lists `--skip-tunnel` for local MCP only alongside the hosted relay flow. This gives users a documented way to avoid the relay mode discussed on HN, but there is no evidence the option was added in response to that commenter or that every AI-client workflow supports the same local-only path. — [HN relay discussion, 2026-07-04](https://news.ycombinator.com/item?id=48784367); [v1.0.20 installer documentation](https://www.npmjs.com/package/lockin-mcp/v/1.0.20?activeTab=readme)
- **Privacy is qualified rather than denied:** July 2026 policy language explicitly documents server relevance checks, scoped event/productive-dwell retention, account linkage, marketing analytics, and no full-history upload/no sale/no sharing with connected AI agents. This is more precise than the homepage shorthand “never your history” and should be the controlling source in any summary. — [Privacy policy, July 2026](https://www.lockinmcp.com/privacy); [homepage](https://www.lockinmcp.com/)
- **Recovery/support responsibility remains important:** the vendor exposes a bug/feature report form and says platform details/install logs help, while its terms place hosts-file/system-configuration responsibility on the user. Current sources do not provide an independently tested guarantee that uninstall always restores every hosts entry or that paid-license refunds follow a particular policy. — [LockIn FAQ/report instructions](https://www.lockinmcp.com/faq); [Terms, June 2026](https://www.lockinmcp.com/terms); [Launchtory documentation-review caveats](https://launchtory.com/projects/lockinmcp)

The second commit (“Add files via upload,” 2025-12-14) added the implementation but is not evidence that a reported problem was fixed. — [Repository commit history](https://github.com/AceAchyut/distraction-killer-ai/commits/main/); [README](https://github.com/AceAchyut/distraction-killer-ai/blob/0e4228babfdd068abdb3dea6e1edfe0d980a8974/README.md); [issue list](https://github.com/AceAchyut/distraction-killer-ai/issues)

- A truthful maintenance summary should use three labels: **discontinued** for brom, **no subsequent public code change visible** for AWF and Distraction Killer AI after their last pushes, and **current package releases without a mapped public changelog** for LockIn. “Unmaintained” and “fixed” would each assert more than the sources establish. — [brom.ai](https://brom.ai/posts/using-machine-learning-to-block-distractions/); [AWF commits](https://github.com/coolvision/awf/commits/master/); [Distraction Killer AI commits](https://github.com/AceAchyut/distraction-killer-ai/commits/main/); [npm LockIn releases](https://registry.npmjs.org/lockin-mcp)

### Gaps

- LockIn’s actual end-user cancellation/refund experience, support responsiveness, uninstall/hosts-restoration behavior, server-data retention periods, task-aware false-positive rate, relay security testing, and mobile expectations need direct testing or customer evidence before becoming factual complaint claims.
- Independent runtime tests remain necessary for AWF’s parsing/rendering vulnerabilities and Distraction Killer AI’s toggle/close-tab behavior. Until then, these are explicit static findings and reasoned risks, not observed incidents.
