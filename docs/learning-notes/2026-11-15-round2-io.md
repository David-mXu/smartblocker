# Round 2: hardening follow-ups — what the second pass taught

## Context

The 2026-11-14 fix round closed with three deliberate follow-ups (a
resume-enforcer harness, a rejected-rebuild reset, the remaining
cache-commit pattern, a nightly CI lane) plus six documented residual
findings. This round landed all of them plus what the leftovers exposed.

## What ran

Five builders, disjoint file ownership, same playbook as round 1:

1. `centroidsInFlight` — the auditor's original premise turned out
   half-wrong (the `finally` DID clear on rejection); the real defects were
   dedupe waiters rethrowing a shared transient failure and an
   un-identity-guarded clear. Waiters now treat a rejected build as "no
   build in progress" and start a fresh one; the builder itself still fails
   closed once.
2. Cache-commit-after-write finished in `settings.ts`, `lock.ts`
   (write + merge paths, merge body untouched), and `profile-store.ts` —
   proven the strong way, with a `git stash` A/B against real modules plus
   injected storage failures: 5/6 scenarios served phantom state before,
   0/6 after.
3. `scripts/resume-enforcer-test.mjs` — 18 cases pinning the onboarded
   gate (both paths), lock deferral, cold-boot vs SW-reap,
   missed-while-asleep, and the lead-not-moving-the-instant schedule
   guarantee. Zero production changes needed: installing a mocked `chrome`
   global before a dynamic import of the whole graph works (the
   `usage-stats-test.mjs` pattern), because `shared/api.ts` binds at
   import time.
4. Companion hardening: drift-detector 2 now uses the same honest-tick
   reference as detector 1 (a drifted "now" is an unsafe judge of what is
   already expired); `partner_arm_at` stamps strictly upward like the
   redeem path; the four partner IPC commands require an authenticated
   connection — a PRODUCT DECISION (David's, 2026-11-15): enrollment is
   deliberately UI-only (`#locks` → Accountability partner); the bare CLI
   `partner add-key|arm|begin|redeem` is refused, `partner-keygen/sign`
   stay offline. Each fix was proven fault-detecting by reverting it and
   watching its new test fail (python suite grew 9→14 checks).
5. Title-rule ReDoS guard (compile cache + authoring-time refusal on >8
   gaps / no >=2-char literal; stored rules grandfathered) and an oEmbed
   resolution quota (25/tab/generation + 500/rolling-hour, exhaustion
   indistinguishable from a failed lookup so the page gets no oracle).

## New findings this round surfaced

- **The vision audit's `#allowance` id list was 7/24 wrong.** The finding
  (§7 lacked the section) was right, but the scraped-id evidence was partly
  fabricated and missed 9 real ids. The doc builder's contract requirement
  — verify every id against source before it enters §7 — caught it. Treat
  every agent-scraped artifact as a hypothesis, not evidence.
- **`e2e-reward-test` was the sixth `enabled` ripple.** Neither CLAUDE.md's
  Commands list nor either audit round mentioned it; its first-ever run
  under the new default failed 6 checks, all fixed by one explicit
  `{enabled:true,onboarded:true}` seed before its intentional lock arms.
  The pattern now has six instances; any NEW suite must seed blocking
  state explicitly.
- **`e2e-companion-test` has a tail-of-chain flake signature**: "extension
  did not load (attempt 1), relaunching" followed by a dead NM connection —
  twice now (rounds 1 and 2), passing 64/64 solo both times. Named
  follow-up: force a fresh daemon registration on relaunch or fail fast.
